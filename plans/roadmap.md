## 1. Обзор

**МедЗвон** определяет намерение звонящего по сырому тексту, который выдаёт движок speech-to-text (STT). Вывод STT зашумлён: он путает фонетически похожие слова с **разными смыслами** («перенести» слышится как «принести»), рвёт слова по границам («записаться» → «за писаться»), теряет окончания, а на тишине/шуме выдаёт бессмыслицу. Классификатор должен сопоставлять такой текст одному из **10 фиксированных намерений** — 6 доменных (`BOOK`, `CANCEL`, `RESCHEDULE`, `INFO`, `OPERATOR`, `COMPLAINT`), 3 конверсационных (`GREETING`, `FAREWELL`, `THANKS`) и `UNCLEAR` — где `UNCLEAR` является первоклассным, ожидаемым результатом, а не ошибкой.

**Жёсткие ограничения:**
- **Без внешних LLM/API** — метод детерминированный и быстрый (этот код выполняется до/вместо обращения к модели).
- **Чистый JavaScript (ванильный Node.js), ESM** — `"type": "module"`, `import`/`export`, ноль зависимостей, только стандартная библиотека Node.
- **Тесты:** `node:test` + `node:assert/strict`, файлы `*.test.js` рядом с исходниками, запуск через `node --test`.
- **Детерминизм:** классификация — чистая функция от входной строки — без `Date.now()`, без `Math.random()`, без замен, без I/O внутри классификатора.
- **Безопасность:** линейные проходы `O(n)`, ReDoS-безопасные литеральные паттерны, без `eval`/`new Function`/`child_process`, длина входа ограничена на старте, `null`/пусто → `UNCLEAR` (никогда не бросать исключение).

**Артефакты (оцениваются):** (1) код в `src/` с зелёным `node --test`, включая все 11 примеров из брифа; (2) mermaid-схема пайплайна, читаемая **без** чтения кода; (3) письменное рассуждение, аргументирующее порядок этапов, метод сопоставления и поведение при низкой уверенности.

## 2. Финальная архитектура

Одна ответственность на файл; чистые функции в ядре; константы отделены от логики.

```
src/
  thresholds.js      — все настраиваемые константы (больше нигде нет magic numbers)
  normalize.js        — guard (null/пусто/короткий ввод) + lowercase + очистка пунктуации + схлопывание пробелов + ограничение длины
  tokenize.js          — разбиение на униграммы и биграммы
  conversational.js    — детекция приветствия/прощания/благодарности: точное совпадение по маркерам + приоритет
  intents.js            — 6 доменных намерений: взвешенные записи униграмм + биграмм (включая STT-разрывы вроде «за писаться»)
  score.js              — точный скоринг доменных намерений: сумма весов совпавших записей
  fuzzy.js              — Левенштейн-фолбэк: частичный вес для близко совпавших токенов, только против малого словаря
  classify.js           — оркестратор: guard → normalize → tokenize → conversational → score → fuzzy → resolve → объект-результат
  index.js              — публичный API: export classify(text)
```

Тесты: `src/<module>.test.js` рядом с каждым модулем; плюс `src/examples.test.js` для 11 сквозных приёмочных кейсов.

**Контракт публичного API** (полные формы данных см. в `architecture.md`):

```js
import { classify } from './src/index.js';

classify(text) → {
  intent:    'BOOK' | 'CANCEL' | 'RESCHEDULE' | 'INFO' | 'OPERATOR' | 'COMPLAINT'
           | 'GREETING' | 'FAREWELL' | 'THANKS' | 'UNCLEAR',
  confidence: number,          // 0..1, нормализованная
  scores:    { BOOK, CANCEL, RESCHEDULE, INFO, OPERATOR, COMPLAINT }, // сырые взвешенные скоры (только доменные)
  matched:   { BOOK: [...строки записей], CANCEL: [...], ... }        // что сработало, для отладки + диалогового движка
}
```

`UNCLEAR` выдаётся с `confidence` лучшего (отвергнутого) кандидата и полными `scores`/`matched`, чтобы диалоговый движок мог решить, переспросить ли, эскалировать или подсказать. Конверсационные намерения (`GREETING`/`FAREWELL`/`THANKS`) детектятся отдельным шагом по точным маркерам и не попадают в `scores` — они бинарно совпадают, а не взвешиваются.

## 3. Пайплайн (7 этапов, упорядоченных)

Порядок осознанный и сам по себе является критерием оценки. Краткое описание; **полная спецификация этапов (цель / входы / выходы / ключевая логика / почему в этом месте)** и **эссе «почему такой порядок»** — в `pipeline.md`.

| # | Этап | Цель | Почему он здесь (кратко) |
|---|------|------|--------------------------|
| 1 | **Guard** | `null`/пусто/`len < guardMinLength` → сразу `UNCLEAR` | Максимально дешёвый отказ; требуется coding-standards; экономит всю последующую работу над мусором |
| 2 | **Normalize** | lowercase, убрать пунктуацию, схлопнуть пробелы, обрезать до `maxInputLen` | Делает сопоставление нечувствительным к регистру/форме; ограничивает работу; должен идти до токенизации |
| 3 | **Tokenize** | выдать униграммы + биграммы | Биграммы несут сигнал фразы; униграммы — одиночные сильные глаголы |
| 4 | **Conversational** | детектнуть приветствие/прощание/благодарность по точным маркерам; приоритет `FAREWELL` > `THANKS` > `GREETING` | Дешёвое точное совпадение; распознаёт конверсационное намерение отдельно от доменного, не перебивая его |
| 5 | **Score (точный)** | суммировать веса совпавших записей по доменным намерениям | Дешёвый, детерминированный основной сигнал; биграммы весомее униграмм; «запись» одна ≈ 0 веса |
| 6 | **Fuzzy fallback** | если max сырой скор `< fallbackThreshold`, Левенштейн каждого токена (len ≥ `minTokenLenForFuzzy`) против словаря → частичный вес | Выполняется только когда точное совпадение слабое; даёт «принести» частично поддержать RESCHEDULE — но никогда не решает один |
| 7 | **Resolve** | доменное намерение выигрывает, если очищает пороги; иначе конверсационное; иначе `UNCLEAR` | Двухуровневое решение: доменное доминирует над конверсационным; строгий UNCLEAR как честный фолбэк |
| 8 | **Result** | собрать `{ intent, confidence, scores, matched }` | Полная картина для диалогового движка и отладки |

**Почему такой порядок (сжато — полное эссе в `pipeline.md`):** дёшево отсеять до начала работы (1); почистить один раз, до любого сопоставления (2); вывести единицы сопоставления до скоринга (3); детектнуть конверсационные маркеры дешёвым точным совпадением (4); сначала попробовать дешёвый точный путь и эскалировать в дорогой фаззи только при слабости (5→6); принять решение о приёме/отказе последним, когда все улики собраны (7); выдать полный, отлаживаемый результат (8). Это поэтапный накопитель улик, а не один большой `if/else`.

## 4. Ключевые принципы дизайна

Эти четыре принципа несущие — каждое решение по модулю должно проверяться на соответствие им.

**П1 — Ни один токен не решает намерение в одиночку.**
Намерение = агрегат (веса биграмм-фраз) + (веса одиночных сильных глаголов) + (частичные фаззи-веса) + (строгие пороги). Фонетическая путаница вроде «принести» **без контекста** → `UNCLEAR`; «принести запись … вместо» → `RESCHEDULE`, потому что *другие* сигналы (униграмма «вместо», фаззи-частичное «принести»≈«перенести») складываются. Двусмысленный токен никогда не несёт решение сам по себе.

**П2 — Детерминизм, без замен.**
Классификация — чистая функция от входа. **Нет** словаря замен «слово → слово» (исходная идея «словаря STT-исправлений» явно отброшена). Словари и пороги живут только в `intents.js` / `thresholds.js` — никаких magic numbers в логике. Без `Date.now()` / `Math.random()` в решающем пути.

**П3 — Безопасность.**
Линейные проходы `O(n)` по входу; без вложенных сканов. Левенштейн выполняется **только** на фолбэке и **только** против малого словаря намерений (не против открытого лексикона); токены короче `minTokenLenForFuzzy` исключаются из фаззи (слишком шумные). Регулярки (если есть) — литеральные паттерны, ReDoS-безопасные. Длина входа ограничена на входе. Без `eval` / `new Function` / `child_process`.

**П4 — Строгий UNCLEAR: лучше переспросить, чем ввести в заблуждение.**
Если система один раз неверно прочтёт «принести» как «принести что-то в клинику» вместо «перенести запись», разговор пойдёт не туда и его трудно вернуть. Поэтому при низкой уверенности или сильной неоднозначности система **переспрашивает** (`UNCLEAR`), а не угадывает. Пороги (`minConfidence`, `ambiguityGap`) — выражение этого принципа и настроены строго.

**П5 — Конверсационные намерения: доменное доминирует.**
Приветствие, прощание и благодарность распознаются отдельным шагом по точным маркерам. Они **никогда не перебивают доменное намерение**: «здравствуйте хочу записаться» → `BOOK`, а не `GREETING`. Конверсационное намерение возвращается только когда доменных улик нет вовсе (доменный скор ниже `domainSilenceThreshold`). При смешанных маркерах действует приоритет `FAREWELL` > `THANKS` > `GREETING` — прощание это терминальный сигнал конца разговора.

**Критический под-принцип — фонетическая неоднозначность это НЕ таблица опечаток.**
Пары вроде «принести ↔ перенести» — это **фонетическая неоднозначность с разными смыслами**, а не опечатки с известным исправлением. «Принести» — само по себе валидное слово («принести справку»). Поэтому **нет** таблицы замен; решают контекст + фаззи-сопоставление. Двойственно, **разорванные слова НЕ склеиваются явно** — отброшенный шаг «склейки слов» заменён ловлей разрывов как биграммных записей в словаре (например, биграмма `за писаться` — сигнал `BOOK`).

## 5. Дизайн словаря намерений (кратко)

`intents.js` определяет по каждому намерению два взвешенных списка: `unigrams` и `bigrams`. **Биграммы весомее униграмм.** Одиночное родовое существительное вроде «запись» должно быть **слабым/≈0**, потому что встречается в контекстах `BOOK`, `CANCEL` и `RESCHEDULE` — если дать ему вес `BOOK`, получатся ложные срабатывания на `CANCEL`/`RESCHEDULE`. Одиночные **глаголы намерения** («отменить», «пожаловаться», «поговорить») сильны даже как униграммы, потому что семантически однозначны.

Сильные биграммы-фразы по намерениям (стартовый набор — полный дизайн и веса см. в `intent-vocabulary.md`):

- **BOOK:** `за писаться` (STT-разрыв), `записаться к`, `записаться на`, `хочу записаться`
- **CANCEL:** `отменить запись` (биграмма) + униграмма `отменить` (сильная — переживает слова-паразиты между ней и «запись»)
- **RESCHEDULE:** биграмма `перенести запись` + униграмма `вместо` (сильная); фаззи `принести`≈`перенести` как дополнение
- **INFO:** `сколько стоит`, `скажите сколько`, униграмма `стоит` (сильная — несёт пример 7, где «скока» не нормализуется)
- **OPERATOR:** `поговорить с человеком` и `с человеком` (оба порядка), униграммы `человеком`/`роботом`/`оператор`
- **COMPLAINT:** `хочу пожаловаться`, униграммы `пожаловаться`/`безобразие`/`жалоба`
- **UNCLEAR:** без словаря — это фолбэк-результат.

**Конверсационные намерения** (детектятся отдельным шагом `conversational.js`, только точное совпадение — без взвешивания и без фаззи):

- **GREETING (приветствие):** `здравствуйте`, `здрасте`, `добрый день`, `доброе утро`, `добрый вечер`, `привет`
- **FAREWELL (прощание):** `до свидания`, `всего доброго`, `всего хорошего`, `до встречи`, `пока`
- **THANKS (благодарность за помощь):** `спасибо`, `спасибо большое`, `благодарю`, `благодарность`

Приоритет при смешанных маркерах: `FAREWELL` > `THANKS` > `GREETING`. Намеренно **не** входят в маркеры неоднозначные с шумом формы вроде «алё»/«ало», чтобы бессмыслица («ыаыы ало алё») оставалась `UNCLEAR`.

**Сопоставление 11 примеров → сигналы** (главный критерий оценки — испорченные кейсы 5–9 проверяют дизайн) дано полностью в `intent-vocabulary.md`. Сжато:

| # | Текст STT | Ожидается | Выигрышные сигналы |
|---|-----------|-----------|--------------------|
| 1 | «здравствуйте хочу записаться к терапевту на завтра» | BOOK | биграммы `хочу записаться`, `записаться к`; маркер `здравствуйте` (GREETING) не перебивает доменное намерение |
| 2 | «мне нужно отменить запись на пятницу» | CANCEL | биграмма `отменить запись` |
| 3 | «скажите сколько стоит приём кардиолога» | INFO | биграммы `скажите сколько`, `сколько стоит` |
| 4 | «это безобразие я час жду на линии хочу пожаловаться» | COMPLAINT | униграммы `безобразие`, `пожаловаться` |
| 5 | «хочу за писаться к врачу на вторник» | BOOK | биграмма `за писаться` (STT-разрыв пойман как запись словаря) |
| 6 | «мне ну это самое отменить наверное запись» | CANCEL | униграмма `отменить` (сильная; слова-паразиты ломают биграмму, поэтому глагол несёт её) |
| 7 | «скока стоит прием у лора» | INFO | униграмма `стоит` (сильная; «скока» не нормализуется, но и не нужна) |
| 8 | «хочу с человеком поговорить а не с роботом» | OPERATOR | биграмма `с человеком` + униграммы `человеком`/`роботом` |
| 9 | «принести запись на среду вместо четверга» | RESCHEDULE | униграмма `вместо` (сильная) + фаззи `принести`≈`перенести` частично — контекст побеждает, двусмысленный токен не решает один |
| 10 | «ыаыы ало алё» | UNCLEAR | нет совпадений со словарём → скор 0 → `UNCLEAR` |
| 11 | «спасибо до свидания» | FAREWELL | доменный скор 0 → конверсационные маркеры `спасибо` (THANKS) + `до свидания` (FAREWELL) → приоритет FAREWELL |

## 6. Направляющие по порогам

Все пороги живут в `thresholds.js`. Значения ниже — **стартовые точки** — их НУЖНО подстроить под 11 примеров (см. §7 шаг 9 и `test-strategy.md`).

| Константа | Смысл | Стартовое значение |
|-----------|-------|--------------------|
| `guardMinLength` | Строки короче этого (после trim) → сразу `UNCLEAR` | `3` |
| `maxInputLen` | Жёсткий лимит длины входа (ограничивает всю последующую работу) | `500` |
| `minConfidence` | Нормализованная уверенность топ-намерения, ниже которой → `UNCLEAR` (абсолютная слабость) | `0.35` |
| `ambiguityGap` | Требуемый нормализованный разрыв `top1 − top2`; меньше → `UNCLEAR` (неоднозначность) | `0.15` |
| `fallbackThreshold` | Если топ **сырой** скор ниже этого — запустить фаззи-этап | `3.0` (≈ одна сильная биграмма) |
| `minTokenLenForFuzzy` | Токены короче этого исключаются из Левенштейна (слишком шумные) | `4` |
| `domainSilenceThreshold` | Max доменный скор ниже этого — доменных улик нет, допускается конверсационное намерение | `0.5` |
| `conversationalConfidence` | Уверенность конверсационного намерения при чистом точном совпадении маркера | `0.9` |

**Константы весов** (также в `thresholds.js` или `intents.js`):

| Константа | Смысл | Стартовое значение |
|-----------|-------|--------------------|
| `strongBigramWeight` | Высокоуверенная биграмма-фраза (например, `отменить запись`) | `3.0` |
| `mediumUnigramWeight` | Семантически однозначный глагол (например, `отменить`, `пожаловаться`, `стоит`, `вместо`) | `2.0` |
| `weakUnigramWeight` | Родовое/двусмысленное существительное (например, `запись`) | `0.3` (или `0`) |

**Конверсационные константы** (тоже в `thresholds.js`):

- `conversationalPrecedence = ['FAREWELL', 'THANKS', 'GREETING']` — приоритет при смешанных маркерах (прощание терминально, важнее благодарности, благодарность важнее приветствия).
- `conversationalConfidence` — уверенность конверсационного намерения при точном совпадении (детекция бинарная, поэтому высокая и постоянная, а не взвешенная).
- `domainSilenceThreshold` — порог, ниже которого домен считается «молчащим», и конверсационное намерение может выиграть.

**Рекомендуемая модель нормализации уверенности:**
Определить по намерению `referenceScore` (сырой скор, который выдаёт чистая эталонная фраза этого намерения — константа в `thresholds.js`). Тогда:
- `confidence_i = clamp(score_i / referenceScore_i, 0, 1)`
- Резолвинг: если `max(confidence_i) < minConfidence` → `UNCLEAR`; иначе если `confidence_top1 − confidence_top2 < ambiguityGap` → `UNCLEAR`; иначе `intent = top1`, `confidence = confidence_top1`.

Это разделяет **абсолютную силу** (`minConfidence`) от **доминантности** (`ambiguityGap`), чего один ratio не может. Значения `referenceScore_i` настраиваются так, чтобы чистые примеры попадали в ~0.7–0.9 уверенности. Полный разобранный пример для кейса #9 в этой модели — в `intent-vocabulary.md`.

- **Детерминизм:** без времени/сети в тестах; моки `node:test` только если понадобятся (не ожидаются — нет I/O).
- **Импорты:** `import test from 'node:test'`; `import assert from 'node:assert/strict'`; равенство объектов через `assert.deepStrictEqual`.

## 10. Известные ограничения и будущая работа

- **Негация не обрабатывается.** «не хочу записываться» сейчас срабатывает как `BOOK`, потому что `записаться` совпадает. Будущий детектор негации (предшествующее «не»/«не хочу») должен подавлять или инвертировать затронутое намерение. Вне объёма v1; задокументировать.
- **Биграммы чувствительны к порядку.** Варианты порядка слов («поговорить с человеком» vs «с человеком поговорить») требуют перечисления обеих биграмм или фолбэка на униграммы. Skip-gram/модель близости обобщила бы это.
- **Словарь курируется вручную и мал.** Он покрывает 11 примеров и очевидных соседей; реальный STT-трафик потребует расширения словаря и перенастройки порогов на размеченных данных.
- **Пороги — стартовые значения, не калиброванные.** `minConfidence`, `ambiguityGap`, `fallbackThreshold` и по-намерению `referenceScore` нуждаются в калибровке на реальном размеченном корпусе STT.
- **Допущение об одном намерении.** Составные запросы («запишите и потом перенесите») не моделируются; v1 возвращает одно намерение.
- **«ё»/диакритика и тяжёлые артефакты STT** (слитые слова, выпавшие гласные сверх спроектированных кейсов) могут потребовать дополнительных правил нормализации.
- **Объём Левенштейна сейчас ок** (малый словарь), но если словарь вырастет, ограничить фаззи несколькими самыми смешиваемыми парами или преиндексировать по длине.
- **Уверенность не калибрована к вероятности.** Это нормализованная мера доминантности; калибровка к эмпирической точности — будущая работа перед доверием ей для авто-маршрутизации против «всегда переспрашивать».
- **Конверсационный словарь мал и консервативен.** «алё»/«ало» намеренно не входят в приветствия (слишком близки к шуму); реальный телефонный «алё» потребует отдельного решения (например, по позиции токена). Смешанные конверсационные фразы сводятся к одному намерению по фиксированному приоритету, а не к комбинации.
